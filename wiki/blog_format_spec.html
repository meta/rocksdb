"Blog" File Format Specification

A unified file format for WAL, Blob, and related data in RocksDB

Status: Implementation in progress  |  Format name: "blog" (portmanteau of "blob" + "log")

File-Level Structure

A blog file consists of three regions: a fixed header with a property section, a body of records, and an optional footer composed of footer records.

+---------------------------------------------------------------------+ | FILE HEADER (40 bytes fixed) | | 96-bit magic, schema version, checksum type, compact record type, | | flags, escape sequence, reserved, property section size, checksum | +---------------------------------------------------------------------+ | HEADER PROPERTY SECTION | | Named key-value pairs + 5-byte trailer (compression + checksum) | | Followed by arbitrarily long padding (0x00 or 0xFF) | +---------------------------------------------------------------------+ | FILE BODY | | Sequence of records, each starting with the escape sequence. | | Record types: blob, WriteBatch, preamble-start, footer records. | +---------------------------------------------------------------------+ | FILE FOOTER (optional) | | Footer index records (0xF0), footer properties record (0xF8), | | file checksum info (0xFC, placeholder), locator (0xFF) last. | +---------------------------------------------------------------------+

Header Property Section

Immediately follows the fixed header. Contains only required (uppercase) named properties that the reader must recognize or reject the file. Ignorable (lowercase) properties are stored in separate ignorable properties records in the body. Encoded as:

[name_len: prefix_varint32] [name: name_len bytes] [value_len: prefix_varint32] [value: value_len bytes] ...

Followed by a 5-byte trailer: [compression_type: 1B][checksum: 4B] (same as block-based table). The checksum covers the property data + compression_type, with a context checksum modifier using the incarnation ID at offset kBlogFileFixedHeaderSize. The section may be empty (trailer only) when no required properties are set.

After the property section, arbitrarily long padding (0x00 or 0xFF, differing from the last meaningful byte) aligns the first record's escape sequence. This supports stronger alignment requirements (flush/sync boundaries) or recycling files of all zeros.

Escape Sequences

Decision: 10-byte escape sequence: 6 random bytes + 4 derived bytes. First byte not 0x00 nor 0xFF (distinguishable from padding). Bytes [6-9] = lower32(XXH3_64bits_withSeed(bytes[0-5], seed)), enabling heuristic detection without knowing the header. The seed is kBlogEscapeSeqSeed, plus the log number for WAL files, so a WAL header is only valid under its own log number.

Escape sequences must be 32-bit aligned in the file. The first 4 bytes (little-endian) serve as the incarnation ID for context checksums.

Primary Roles

  • WAL recycling detection: When recovery encounters undecodable data, scan for our escape sequence. If not found, the data is stale/recycled (different random sequence). The kBlogFileRecycled flag in the header marks that this file itself was recycled and may carry such a stale tail; it only governs this happy-path tail tolerance, never header-mismatch recovery. A recycled WAL renamed to a new log number, but whose header has not yet been rewritten, fails the log-number-seeded escape sequence check.
  • Non-linear recovery: After corruption, scan forward for the next escape sequence to resume recovery (kSkipAnyCorruptedRecords).
  • Record boundary discovery: Find record boundaries from any file position.

Decision: user-defined timestamp metadata retries follow legacy WAL behavior.

A WAL may contain multiple timestamp-size records, but each column family may appear only once across those records. Both legacy and blog WAL readers reject a repeated column family as corruption, even when its timestamp size is unchanged.

The writer updates recorded_cf_to_ts_sz_ before attempting to write the metadata and does not undo that update after an I/O error. Updating only after the write call returns success would allow duplicate metadata on retry: the complete record can have been appended before a subsequent filesystem flush fails.

This deliberately preserves the legacy limitation: if the metadata was actually lost, including in a later failed flush of buffered data, retrying on the same WAL does not guarantee that it will be rewritten. The bookkeeping records the attempt; it is not evidence that the metadata was persisted.

Format Selection

The record format is determined by the prefix-varint-encoded length field:

  • Value 0 (1 byte): Trivial format (no payload).
  • Values 1–16383 (1–2 bytes): Compact format.
  • 3+ byte prefix varint: Full format. Includes type, pre-payload compression type, and prefix checksum.
  • length = 263 − 1: Unspecified size (full format). Reader scans forward for the next escape sequence, or terminates the record at the end of the file. See below.

Unspecified-Size Records and Their Boundaries

An unspecified-size record is the one record shape that is not self-delimiting. Its payload ends at whichever comes first: the next 32-bit-aligned escape sequence, or the end of the file. For either boundary the reader derives the padding length as the exact trailing run of 0x00/0xFF bytes immediately before it, places the 5-byte trailer immediately before that run, and accepts the boundary only if the trailer checksum authenticates the payload. Without the end-of-file boundary, a record that nothing follows -- the last record of a file abandoned by a crashed process -- could never be read back at all.

Writer restriction. A writer must not use the unspecified-size encoding in a file whose trailing bytes, at the moment a reader may see it, are neither absent nor padding. There is no reader-side remedy for such a file: nothing in it records where the last record stopped, and brute-force scanning for a boundary whose trailer happens to checksum is unsafe -- over a large tail the per-candidate false-accept probability accumulates, and under kNoChecksum the stored trailer value does not depend on the payload at all, so it authenticates nothing.

In RocksDB today exactly one file shape violates that condition: a recycled WAL (kBlogFileRecycled). It is reused without being truncated or zeroed first, so the previous incarnation's bytes remain past the logical end, and they carry a different escape sequence, so neither boundary is reachable. Writers of recycled WALs must therefore keep every record self-delimiting. Every other file is safe:

  • Blob files: records are only ever read by random access at an offset the blob index supplies, never by scanning for boundaries -- including a direct-write file read while it is still open and unsealed.
  • Non-recycled WAL and MANIFEST: written buffered, and preallocated with FALLOC_FL_KEEP_SIZE, so the physical end of the file is exactly its last written byte. That last written byte can still belong to a partially written next record; see the known gap below.
Known gap: partially written next record. A crash (or a partial write, for example on a full disk) can leave only the first few bytes of the next record's 10-byte escape sequence at the end of a non-recycled file. That tail is neither absent nor padding, so an unspecified-size record immediately before it cannot be delimited: no complete escape sequence follows it, and the end-of-file boundary finds the partial escape bytes where the padding and trailer should be. The reader reports an incomplete tail, and the complete unspecified-size record before it is lost, even if it was synced. A sized record in the same position is not affected, because its length delimits it. The format cannot close this gap: a partial escape sequence is a byte string that payload, trailer, or padding bytes can also form, and there is no principled minimum length at which a trailing fragment should count as the start of a record -- 9 bytes, 8, or 1. Any reader-side rescue is therefore a best-effort heuristic. Writers that use unspecified-size records, and users who enable them, accept this gap. In RocksDB, only BlogWalWriter emits them, for batches of at least 16 KiB in non-recycled WALs when blog_wal_streaming_compression is enabled.
Possible future option (not implemented). An opt-in, best-effort reader mode could narrow the gap above. When the end-of-file boundary fails, it would also try each 32-bit-aligned offset within the last 9 bytes of the file whose remaining bytes match a prefix of the file's escape sequence. It would accept such an offset only if the trailer checksum before it authenticates the payload, and keep the partial escape as an incomplete tail. This is a heuristic, not a format guarantee: the shorter the matching prefix, the more likely the match is coincidental, and under kNoChecksum the trailer authenticates nothing. It is recorded here so that reviewers do not re-propose it as a fix.

Note that this is a constraint on the length encoding, not on any particular feature. Anything that cannot know a record's payload size before emitting its prefix -- for instance a future writer that streams compressed bytes to the file rather than buffering and measuring them first -- inherits the same restriction, whether or not it uses streaming compression.

Trivial Record Format (prefix varint value 0)

[escape_seq: 10B] [prefix_varint(0): 1B] [type: 1B] [checksum: 4B] [padding: 0+ B]

For records with no payload (e.g. preamble-start). The checksum covers (prefix_varint + type), with a context checksum modifier. No compression type byte since there is no payload to compress.

Compact Record Format (prefix varint 1–2 bytes, values 1–16383)

[escape_seq: 10B] [prefix_varint length: 1-2B] [payload: length bytes] [compression_type: 1B] [checksum: 4B] [padding: 0+ B]

No type byte — type comes from the header's compact_record_type field. Used for payloads < 16 KiB. The compact format has no separate length checksum; the checksum in the trailer covers the payload and compression_type byte with a context modifier derived from the payload's file offset and incarnation ID. An incorrect length field will cause the checksum to fail because the payload bytes fed to the checksum will be wrong. Furthermore, an incorrect length field fails to locate its own checksum trailer without scanning and must be reported as Corruption. Adding a type byte to the compact format would require including it in the checksum computation (or modifying the escape sequence) to maintain integrity.

Unlike the full format, which may encode its length with an irregular (overlong) prefix varint, a compact record's length must use the minimal prefix varint encoding for its value. A non-minimal 1–2 byte encoding is rejected as corruption before any payload is read. This keeps the unauthenticated compact length structurally checkable even when blog_checksum is kNoChecksum.

Full Record Format (prefix varint ≥ 3 bytes)

[escape_seq: 10B] [prefix_varint length: 3+B] [type: 1B] [compression_type: 1B] [prefix_checksum: 4B] [payload: length bytes] [compression_type: 1B] [checksum: 4B] [padding: 0+ B]

The prefix_checksum covers (prefix_varint + type + compression_type), with a context checksum modifier for defense-in-depth. Validates the length before attempting a potentially large read. The pre-payload compression_type enables streaming decompression without seeking to the trailer.

Known risk: unverified full-format lengths. A full-format length is trusted only when its prefix_checksum is verified, which needs both a checksummed file (blog_checksum other than kNoChecksum) and a reader that verifies checksums. WAL recovery, RepairDB, and ldb always verify; a GetUpdatesSince iterator verifies only when WalIterator::ReadOptions::verify_checksums_ is true (the default). Otherwise a corrupted length is taken as written: the sequential reader keeps reading and retaining file data until it has the claimed number of bytes or reaches the end of the file, and only then reports the record as incomplete or corrupt. One such record can therefore hold up to about twice the remaining size of the file in memory, rather than one record's worth, and on a very large file the allocation can fail. Choosing kNoChecksum for WALs accepts this risk.

Records that don't match the compact_record_type (e.g. footer records) always use full format by encoding the prefix varint with ≥ 3 bytes (irregular encoding), but length 0 is disallowed and must use the trivial record format.

All checksums in blog files (fixed header, property section trailer, record prefix, record trailer) use context checksum modifiers incorporating the incarnation ID, providing defense-in-depth for misplaced data detection even with kNoChecksum.

Compression

Per-Record Compression

Each record's trailer compression_type byte indicates the compression algorithm used for that record's payload. The actual type comes from Compressor::CompressBlock output, not the configured type. This is the same approach used by SST block-based table builders.

Streaming Compression (WriteBatch records only)

When the header property WriteBatchStreamingCompressionType is set, WriteBatch record payloads may use streaming compression across records. Such records use kStreamingCompressionSentinel (0x7F) as their trailer's compression_type byte, indicating "compressed using the streaming algorithm declared in the header."

All streaming-compressed records in a file form a single stream, in file order. For ZSTD this is one frame that is continued, never restarted, by each record; the writer flushes after each record's payload, so a record decodes once all earlier streaming-compressed records in the file have been decoded. The frame need not be ended. Because later records may reference earlier ones, a reader that cannot decode a streaming-compressed record cannot decode any later one in the file.

A record with kNoCompression (0x00) in the trailer is stored uncompressed and is not part of the stream, even when streaming is active, so readers must accept it anywhere among streaming-compressed records. This is a writer-internal escape hatch, not a tunable: a writer must decide to leave a record out of the stream before compressing it, because compressing advances the stream state that later records depend on, so a record cannot be compressed, judged ineffective, and then stored raw. BlogWalWriter writes empty WriteBatch records uncompressed, and writes all later records uncompressed after a write error that may have lost part of the stream.

Non-WriteBatch records (blob records, footer records) are always outside the streaming context and use per-record compression, keeping blob data randomly readable.

Streamed WriteBatch records may use the unspecified-size length encoding, so the writer can stream compressed bytes to the file without buffering and measuring them first. Large records do; small ones stay buffered as sized (usually compact) records, since below one output chunk streaming saves no copy while the unspecified-size framing costs bytes and scan-based reads. Recycled WALs must keep every record self-delimiting (see above) and therefore buffer streamed records into sized records instead.

Currently only ZSTD is supported for streaming compression. The WriteBatchStreamingCompressionType property is required (uppercase first letter), so older readers that don't understand it will reject the file rather than misinterpret streaming-compressed payloads.

Padding Scheme

Padding fills the gap between a record's trailer (or the header property section) and the next escape sequence. The padding byte value is chosen to differ from the last meaningful byte, enabling unambiguous scanning.

Last meaningful bytePad withMandatory?
0x000xFFYes -- at least 1 byte required
0xFF0x00Yes -- at least 1 byte required
Anything else0x00 preferred; 0xFF also legalOnly if needed for alignment

Padding may be arbitrarily long for stronger alignment requirements (for example, rounding up to 512-byte or 4 KiB flush/sync-friendly boundaries) or for recycling a file of all zeros. The reader skips padding by scanning forward over 0x00/0xFF bytes in 4-byte-aligned chunks until finding a byte that is neither, which is the first byte of the next escape sequence (guaranteed to be neither 0x00 nor 0xFF).

Decision deferred: bounding WAL padding scans.

The unbounded scan and buffering cost of long padding runs, including zero-filled recycled WAL tails, follows directly from the decision to permit arbitrary padding. Supporting arbitrary amounts of padding while bounding reader resource use would require a more complex reader implementation.

A future solution should constrain the quantity of padding bytes the writer is permitted to emit. Selection of that limit and changes to the reader are deferred. No padding bound is currently specified or enforced; arbitrarily long padding remains legal.

Context Checksums

Decision (adopted from SST format_version=6): Each record checksum incorporates a 32-bit incarnation ID (first 4 bytes of the escape sequence). Prefix and trivial-record checksums use ChecksumModifierForContext(incarnation_id, record_offset). Payload trailer checksums use ChecksumModifierForContext(incarnation_id, payload_offset), allowing a random-access blob reader to verify [payload][trailer] without reading the record prefix. This is the same mechanism as block-based SST files.

Context checksums provide defense-in-depth for recycling detection and general data integrity verification with zero per-record overhead.

The checksum type is configured via DBOptions::blog_checksum. The same option is intended to govern blog-format internal checksums across file roles.

Footer

The footer is composed of regular records using the full record format, maintaining simple forward parsability. A file is cleanly sealed when a valid footer locator record is the last record. Footer records appear in the order listed below.

On the happy path, format-aware close of an initialized WAL appends the footer, flushes it, trims any stale recycled tail, and closes the file. Closing does not request an additional sync. Crashes, failed finalization, and direct underlying-file closure may leave the WAL unsealed. A WAL truncated after a failed memtable insertion is closed without a footer. Because nothing follows the footer, WAL readers treat damage confined to footer records as an unsealed clean end in every recovery mode, once they can tell that the damaged bytes belong to the footer (see the known gap below).

  1. Footer index records (0xF0): Large metadata like sparse indexes for range queries. Zero or more per file.
  2. Footer properties record (0xF8): Named properties (same encoding as header properties, but the full record format's own trailer provides integrity). At most one per file. The encoded properties plus the record's 5-byte trailer must not exceed kBlogMaxPropertySectionSize (16 MiB), matching the header property-section limit.
  3. Footer file checksum info (0xFC): Placeholder for future use. Would contain a dump of the full file checksum state, allowing the file checksum to be inferred from just reading the tail of the file.
  4. Footer locator record (0xFF): Must be the last record. Contains relative offsets (in 4-byte units) to other footer records, sequential relative to each other in reverse order.
Known gap: torn footer prefix. Because close does not sync the footer, a crash after a clean close can keep any prefix of it, even when every record before it was synced. A reader can recognize footer bytes only after the first footer record's full-format prefix (escape sequence, length varint, record type, compression type) is verified by its prefix checksum; with blog_checksum=kNoChecksum it cannot recognize them at all. A tear before that point is indistinguishable from a torn data record, so it is reported as an incomplete tail. kTolerateCorruptedTailRecords and kSkipAnyCorruptedRecords ignore it, and kPointInTimeRecovery reports it and stops replay at the last complete record before it. kAbsoluteConsistency fails DB::Open, which a legacy WAL closed in the same state would not, because a legacy WAL writes nothing at close. Syncing the footer at close would close this gap at the cost of an extra sync per WAL close; whether to do so is a pending decision.

Footer Locator Payload

[record_type: 1B] [relative_offset_in_4B_units: uint32 LE] ...

First entry: distance from locator's escape_seq backward to the preceding footer record. Subsequent: from the previous entry backward to the next.

WAL Recovery Modes

The escape sequence is the primary mechanism for detecting WAL recycling and for non-linear data recovery. The kBlogFileRecycled flag in the header indicates the file may contain trailing stale data from a previous incarnation.

In every mode, a WAL header that checksums correctly but whose escape sequence does not match the file's log number ends reading of that file. With checksums enabled, the intact checksum shows the escape bytes are as written, so the mismatch means a stale incarnation (a recycled WAL renamed to a new log number before its header was rewritten), not a bitflip: the file is treated as empty (reported as an old log record) in all modes. The stale header's kBlogFileRecycled flag is about the old incarnation and is not consulted here; the flag only marks a happy-path stale tail. A corrupted escape fails the header checksum first (forward-scan disaster recovery is future work). Exception: with blog_checksum=kNoChecksum the fixed-header checksum covers only the incarnation ID (escape bytes [0..3]), so damage to escape bytes [4..9] passes the header check and is misclassified as stale-empty.

Creating a WAL writes its header to the file but does not sync it. Like records, the header becomes durable with the WAL's next sync, which covers the whole file. A crash before that sync can leave a non-recycled WAL empty or holding only a prefix of its header, and can leave a recycled WAL with new header bytes written over part of the previous incarnation's header. A 0-byte WAL has no bytes from which to detect its format, so it is read as an empty WAL in every mode, as a legacy WAL is: nothing is reported, kAbsoluteConsistency opens, and kPointInTimeRecovery continues to the next WAL. Readers treat the other states as corruption. A non-empty incomplete header is reported as an incomplete tail: kAbsoluteConsistency fails DB::Open, kPointInTimeRecovery reports it and stops replay, and kTolerateCorruptedTailRecords and kSkipAnyCorruptedRecords ignore it. A prefix shorter than the 12-byte file magic cannot be told apart from a legacy WAL, so the legacy reader reads it and reports it as a truncated legacy record, with the same per-mode outcome. An invalid header, such as new header bytes over a stale one, is reported as corruption: kSkipAnyCorruptedRecords ignores it, kPointInTimeRecovery stops replay, and the other two modes fail DB::Open. A recycled WAL whose header was not rewritten at all keeps the previous incarnation's intact header and is treated as stale, as above.

Decision deferred: header-only WALs under kAbsoluteConsistency.

A WAL that holds only a non-empty incomplete header carries no user data, yet kAbsoluteConsistency fails DB::Open on it, while a legacy WAL in the same state (empty, because legacy writes no header) opens. A 0-byte WAL is not affected: it already opens, as described above. Whether a non-empty incomplete header with nothing after it should count as an empty WAL in this mode is deferred. Until then no exception is made for such header-only WALs: a non-empty incomplete header is corruption in every case.

Distinguishes tail damage from mid-file corruption.
kPointInTimeRecovery (default) Stop at first inconsistency. Incomplete trailing records tolerated. Recycled trailing data accepted, but reported as an old record, as in legacy WALs: it can stand where unsynced records were lost, so the next WAL is replayed only if its sequence numbers are contiguous. Diagnostic improvement.
kSkipAnyCorruptedRecords On corruption, scan forward for next escape sequence. If found, try to decode and verify; resume if valid. If not found, stop. Ignores IOError and Corruption, matching existing WAL kSkipAnyCorruptedRecords behavior. Once a record is skipped or a streaming-compressed record cannot be decoded, later streaming-compressed records are dropped without decoding, while other records are still recovered. Essential for record discovery after corruption.

ldb dump_wal and RepairDB read blog and legacy WALs in different modes so that both get every readable record. The legacy reader in kTolerateCorruptedTailRecords reports a corrupted record and keeps reading to the end of the file, and it stops quietly at a recycled WAL's stale tail. The blog reader in that mode stops at mid-file corruption (see above); only kSkipAnyCorruptedRecords makes it continue past corruption. So these tools keep kTolerateCorruptedTailRecords for legacy WALs, leaving their behavior unchanged, and use kSkipAnyCorruptedRecords for blog WALs. Because a blog WAL header is verified against the log number, ldb dump_wal requires a blog WAL to keep its original NNNNNN.log file name.

Tailing a live recycled WAL. A failed record with no later boundary may be a write still in progress over stale bytes, so a tailing reader waits for a later poll instead of reporting corruption. The scan for that boundary stops at the failed record's maximum extent plus 4 KiB of padding: exact for trivial records, the compact maximum for compact records, and the authenticated length for full-format records; otherwise it is unbounded. Known gap: trivial and compact lengths are not checksummed, so corruption that makes a larger record's length decode as trivial or compact hides the next boundary, and the tailing reader waits on every poll rather than reporting corruption. This is accepted because the alternative, an unbounded scan after every failed compact record, costs time proportional to the recycled file size on each poll.

WriteBatch Blob Preamble

A blob preamble is a sequence of blob records preceded by a preamble-start record (type 0x11, trivial format, length=0) and followed by the associated WriteBatch record. The blob records contain separated values referenced by file_number = 0 blob references in the WriteBatch.

This functionality is stubbed in the current implementation: the preamble-start record type is defined and can be written/read, but the full preamble flow (in-memory serialization, blob reference encoding) is deferred.

Ignorable Properties Records

Ignorable properties records (kBlogIgnorablePropertiesRecord, type 0x01) carry diagnostic/debugging named properties using the same encoding as the header property section. They may appear anywhere in the file body:

  • Initial writer: immediately after the header, the writer emits an ignorable properties record for its diagnostic properties (dbSessionId, dbHostId, creator, creationTime, role, etc.). The header property section itself contains only required/uppercase properties.
  • File reuse (e.g. manifest reuse): when an existing file is re-opened for appending by a new writer (potentially on a different host or RocksDB version), the new writer emits another ignorable properties record with its own identity and diagnostics. This is why multiple ignorable properties records may appear in a single file.

Restrictions:

  • Only ignorable (lowercase) properties are allowed in these records. Required (uppercase) properties are set once in the header property section and cannot appear here.
  • Readers may skip these records entirely without affecting correctness.

The upper/lowercase naming convention remains useful for distinguishing required vs. ignorable properties when they are combined into a single map or dictionary for inspection.

Replication Log Column Family

Deferred. The blog format supports an "rlog" role hint for replication log storage, with sparse indexes in footer records and in-memory index maintenance. See design notes in the original proposal.

DB Options

  • use_blog_format_for_wals (bool, default false): New WAL files use blog format.
  • blog_wal_streaming_compression (bool, default false): New blog WAL files compress WriteBatch records with cross-record streaming compression of type wal_compression (ZSTD only) instead of per-record compression.
  • use_blog_format_for_blobs (bool, default false): New blob files use blog format.
  • blog_checksum (ChecksumType, default kXXH3): Checksum algorithm for blog format files. ChecksumType enum moved to include/rocksdb/checksum_type.h (from table.h) for use by both table and DB options.
  • blog_timestamp_size (size_t, default 0): "TimestampSize" header property for new blog WAL files. Zero omits the property.

All are immutable DBOptions. Existing legacy WAL and blob files are always readable regardless of these settings.

Compression Manager Integration

  • Blog blob files use the CF's configured compression manager (via MutableCFOptions::compression_manager). Legacy blob files continue to use the builtin manager for backward compatibility.
  • Blog WAL files use per-record compression via Compressor::CompressBlock. The actual CompressionType from CompressBlock output is stored in the record trailer.
  • With blog_wal_streaming_compression, BlogWalWriter instead writes ZSTD cross-record streaming compression, declaring WriteBatchStreamingCompressionType and marking records with kStreamingCompressionSentinel (0x7F). BlogWalReader decodes the stream in file order and accepts kNoCompression records among streamed ones.
